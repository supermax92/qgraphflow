# 対話による要件確認

[English](../../../skills/q-flow/references/guided-intake.md) · [简体中文](../zh-CN/guided-intake.md) · [Русский](../ru/guided-intake.md) · [Português](../pt/guided-intake.md) · [日本語](guided-intake.md) · [Deutsch](../de/guided-intake.md) · [Español](../es/guided-intake.md)

呼び出しと会話を合わせても開始条件が揃わない場合だけ使います。必要なのは**対象**と図が答える**問い**です。それ以外には既定値があり、質問しません。

## 開始条件

| 項目 | 準備完了の条件 | 質問しない内容 |
| --- | --- | --- |
| 対象 | リポジトリ、モジュール、フロー、エンティティ集合、文書が明示され、問いに合う粒度である。動作の問いは1つのフロー、状態は1つのコンポーネントが必要。構造ならリポジトリ／モジュールでよい | — |
| 問い | 知りたいこと、または意図を推定できる図の種類が示されている | — |
| 図の種類 | — | SKILL.md の Author 手順1で意図から決定。既定は `architecture` |
| 粒度 | — | 下記の階層規則で決定。「詳細か簡単か」と聞かない |
| 出力先、言語、図数、CodeGraph 設定 | — | 既存の既定値。出力先は要約で示し、変更可能にする |

不足する項目だけ質問します。動作の問いでリポジトリ／モジュールしか指定されていない場合、不足はフローです。下記の第2ラウンドの入口検索を行い、フローだけ聞きます。会話からスキルが起動された場合も、対象と問いがあればそのまま開始します。

## 最初の一覧確認

実在のモジュールを選択肢にするため、質問前に確認します。範囲は深さ2までのディレクトリとマニフェストの有無だけです。ソースを読まず、入口を検索せず、`codegraph explore` を実行しません。

| 手がかり | ファイル／ディレクトリ | 提供できる意図 |
| --- | --- | --- |
| ビルド | `package.json`、`pom.xml`、`build.gradle*`、`go.mod`、`Cargo.toml`、`pyproject.toml`、`*.csproj` | モジュール候補、言語、フレームワーク |
| 永続化 | `migrations/`、`db/migration/`、`*.sql`、`entity/`、`model/`、ORM マッピング | `er` |
| 配置 | `Dockerfile`、`docker-compose*.yml`、`k8s/`、`helm/`、`charts/` | `deployment` |
| 状態 | 名前に `State`、`Status`、`Phase`、`Lifecycle` を含むファイル | `state` |
| 文書 | `docs/`、`requirements/`、`*.md` の要件文書 | `flowchart`、`usecase` |
| CodeGraph | `.codegraph/` の存在 | 要約に「直接追跡」でなく「CodeGraph」と記す |

最上位ディレクトリが8つを超える場合、ビルド定義のあるものだけ列挙します。空のディレクトリ、コードリポジトリでない場所、プラグイン自身の導入先の場合は、対象リポジトリのパスか要件文書を尋ね、モジュール候補を出しません。

## 意図の選択肢

図が答える問いとして提示し、必要な対象階層と短いコスト表記を付けます。最大4件、一覧確認で裏付けられるものだけにし、ちょうど1件を推奨します。既定の推奨はリポジトリ全体の構造概観です。

| 選択肢 | `meta.diagramType` | 必要な対象 | コスト | 提示条件 |
| --- | --- | --- | --- | --- |
| システムの構成と依存関係 | `architecture` | リポジトリ／モジュール | 速い | 常に |
| 実行場所と配置 | `deployment` | リポジトリ | 速い | 配置の手がかり |
| 保存データと関連 | `er` | リポジトリ／モジュール | 速い | 永続化の手がかり |
| 型の種類と関係 | `class` | モジュール | 速い | ビルドの手がかり |
| 誰が何をできるか | `usecase` | リポジトリ／モジュール | 速い | 文書または公開入口 |
| 誰が誰をどの順で呼ぶか | `sequence` | 1つのフロー | 呼出追跡 | 常に |
| フローの判断と分岐 | `flowchart` | 1つのフロー | 呼出追跡 | 常に |
| データの移動と変化 | `dataflow` | 1つのフロー | 呼出追跡 | 常に |
| 対象が経る状態 | `state` | 1つのコンポーネント | 呼出追跡 | 状態の手がかり |

構造意図（`architecture`、`deployment`、`er`、`class`、`usecase`）では主に宣言とマニフェストを読みます。動作意図（`sequence`、`flowchart`、`dataflow`、`state`）は実行経路を追うためコストが高くなります。表記はその説明であり推奨を変えません。

## 対象階層と図の予算

ノード単位は対象の1段下です。

| 対象 | ノード単位 |
| --- | --- |
| リポジトリ全体 | モジュール／サービス |
| モジュール | コンポーネント／クラス |
| 1つのフロー | ステップ／関数 |
| エンティティ集合 | テーブル |

1図は Viewer の経路予算内、約10ノード・9接続に収めます。問いに必要な主ノードを残し、省略項目は `facts` または引き渡しメモに記します。最初の図を見た後の追加依頼で掘り下げます。選んだノードを対象とし、新しい `<node-scope>-<diagram-type>/` に出力します。最初に掘り下げの要否を聞きません。

## 質問

対象と意図を1つのメッセージで質問します。クライアントに構造化質問ツールがあれば使い、なければ番号付きの文章にします。固有のツール名は仮定せず、ユーザーの言語で尋ねます。

```text
どの部分？ 1 注文  2 支払い  3 在庫  4 リポジトリ全体（推奨）
図で知りたいことは？
  a 構成と依存関係 — リポジトリ／モジュール · 速い（推奨）
  b 呼び出し順 — 1つのフロー · 呼出追跡
  c 保存データと関連 — リポジトリ／モジュール · 速い
  d 実行場所 — リポジトリ · 速い
```

質問したら**ターンを終了して回答を待ちます**。回答を仮定しません。このラウンドが終わる前に `index.html`、`graph.json`、その他の出力を書きません。

## 第2ラウンド

構造意図は第1ラウンドで終了します。第2ラウンドは次の場合だけで、第3ラウンドはありません。

- **対象が未確定**：実在するモジュールを最大3件提示し、1件を推奨。
- **意図が2つ**：主意図を選び、もう一方は別の図にできると説明。
- **動作意図で対象がリポジトリ／モジュール**：入口を調べ、最大4フローを提示。`rg -l` でファイル名と注釈（`*Controller*`、`*Handler*`、`*Listener*`、`*Consumer*`、`main`、`@RestController`、`@KafkaListener`、ルートデコレーター）を探し、関数本体は読まない。既に使われた語に合う候補を優先。多すぎればパッケージ単位で選んでもらい、その選択を第2ラウンドとする。

「何でも」「任せる」などは推奨項目を選び、その仮定を要約に記します。

## 要約して開始

1行で要約したら、再確認せず証拠収集に入ります。ユーザーは随時訂正できます。

```text
<種類> · <対象> · <問い>に回答 · <ノード単位>、約10個 · <出力先> · <CodeGraph | 直接追跡>。後でノードの掘り下げも依頼できます。
```

例：`sequence · 注文モジュールの OrderController.create · 注文の呼出順 · ステップ単位、約10個 · docs/qgraphflow/order-create-sequence/ · 直接追跡。後でステップの掘り下げも依頼できます。`
